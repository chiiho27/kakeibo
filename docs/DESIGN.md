# 家計簿V3 PWA 設計メモ（第1段階）

設計指示書（2026/11/08）に沿った調査結果と、採用技術・同期方式の案。
家計の実データ・秘密値はこのリポジトリに置かない（公開リポジトリのため）。

## 1. 調査結果

### 既存リポジトリ（chiiho27/kakeibo）
| 項目 | 現状 |
| --- | --- |
| 構成 | `index.html` 1ファイル（約100KB、HTML/CSS/JSを直書き）＋ `sw.js` ＋ `manifest.json` ＋アイコン。ビルド工程・テストなし |
| 公開 | GitHub Pages（main ブランチ直下）。公開リポジトリ |
| 端末保存 | localStorage（取引・設定・同期状態をJSONで丸ごと保存） |
| 同期 | 別途作成した Apps Script（AppSync）へ合言葉付きPOST。アプリ側の全件で 01_Raw_Data の B〜I 列を日付順に書き直す方式 |

既存アプリの同期は、指示書の確定事項と次の点で合わないため、作り直しの対象とする。
- アプリの全件でスプレッドシートを上書きする（スプレッドシートが正本ではない）。
- 行を並べ替える。取引に不変IDがなく、内容（日付・金額・方法・詳細）で照合している。
- 端末側のデータが消えると、スプレッドシート側の削除と区別しにくい（実際に端末データの消失が発生）。
- 合言葉1つで読み書きできる。端末ごとの取り消しができない。

`_AppSync` シートは、この既存同期が作った「前回書き写した行のキー」の控え。元の家計簿の機能ではない。

### スプレッドシート（読み取りのみで確認）
- 01_Raw_Data：4行目見出し。A 取引ID（`TX-yyyymmdd-連番`。行の位置で変わるため一意キーにしない）、B〜I 入力列、J 年月、K 週番号、L 登録日時、M 重複チェックキー（`yyyymmdd|金額|方法|詳細`）、N 以降は費目候補の数式。空いている列はない。
- 03_Card_Import：4行目見出し。A 取込ID、B 取込日時、C 利用日、D 利用先・内容、E 金額、F 入出金方法、G 区分、H 費目、I 満足度、J 照合・重複判定、K 取込状態、L データ元、M 元ファイル名、N 確認メモ、O 以降候補数式。
- 96_Drop_Down：区分別の費目一覧、区分・費目・詳細・入出金方法・割合・目安額・月別表示名・表示順。
- 共有設定：リンクを知っていれば誰でも閲覧できる状態だった。新しい仕組みはこの公開状態に依存しない。
- 未確認：数式・入力規則・保護範囲。

### 既存 Apps Script（コード.gs：カード明細取込）
- `readCardCsvFiles`（CSV→03_Card_Import）と `applyApprovedCardRows`（取込可→01_Raw_Data）は `LockService.getDocumentLock()` で直列化している。
- 01_Raw_Data への書込順：B:D（利用日・金額・区分）→ F:I → L（登録日時）→ `flush` → E（費目）。E の入力規則が D に連動する候補を参照するため。
- 追記位置は B 列の最初の空行（`findFirstBlankByColumn_`）。上限を超えると行を挿入する（数式範囲 4986 行の外になる点に注意）。
- 処理済みファイルはファイルIDで判定（DocumentProperties）。費目推測は 店舗基本設定 → Raw確定履歴 → 店名ルール → 空欄。
- 旧同期（アプリ連携.gs）は `getScriptLock()` を使っており、カード取込とは互いに守れていなかった。

新しい API（`gas/アプリAPI.gs`）は、同じドキュメントロック・同じ書込順・同じ空行判定を使う。上限（4986行）を超える追加は行を挿入せず、エラーとして返す。データ元（I列）は既存値の「手入力」を使い、アプリ由来であることは台帳（`_AppSync`）に記録する。

## 2. 採用技術と選定理由

| 役割 | 採用 | 理由 | 採用しなかった案 |
| --- | --- | --- | --- |
| 画面 | React ＋ TypeScript ＋ Vite | フォーム・複数画面・状態を部品単位で整理でき、型で列対応や同期データの取り違えを防げる。Vite は設定が少なく、ビルドが速い | 既存の1ファイル直書き：規模が大きくなり不具合が増えたため。Preact：軽いが、使う部品（Radix・Lucide）との互換性確認が増える |
| PWA | vite-plugin-pwa（Workbox） | キャッシュ・更新処理を自作すると、古い画面が残るなどの不具合が起きやすい（既存版で実際に発生）。更新はユーザー操作で反映し、未送信データには触れない | Service Worker の手書き |
| 端末保存 | IndexedDB ＋ idb（薄いラッパー） | 取引・未送信キュー・下書きを別々に永続化でき、トランザクションで「端末保存の完了」を確定できる。idb は約1KBで、生の IndexedDB の書き間違いを減らせる | localStorage：容量・同時書込・部分更新に弱い。Dexie：高機能だが今回は不要 |
| 永続化の要求 | `navigator.storage.persist()` | ブラウザーによる自動削除を受けにくくする（保証ではない） | — |
| アイコン | lucide-react（24px・線幅2） | 指示書の確定事項。線の太さと形が統一されている | — |
| ダイアログ・ボトムシート | Radix UI Dialog | フォーカス管理・読み上げ・Esc 閉じを正しく実装済み。見た目は自前で付けられる | 自作：フォーカス管理の抜けが起きやすい |
| 日付 | ライブラリなし。日付は `YYYY-MM-DD` 文字列で保持 | `new Date('2026-11-08')` は UTC として解釈され前日にずれる。文字列のまま扱えば時差の影響を受けない。表示は yyyy/mm/dd に整形 | date-fns 等：今回の処理量では不要 |
| テスト | Vitest ＋ fake-indexeddb | 週予算の日割り、日付、キューの冪等性、照合規則を自動で確認できる | — |
| 配信 | GitHub Pages（GitHub Actions でビルド） | 既存の公開先・URLを引き継げる。HTTPS。公開リポジトリなら費用なし | Vercel・Netlify：新しいアカウントと設定が増える |
| 連携処理 | 既存スプレッドシートの Apps Script に API ファイルを追加し、ウェブアプリとして公開 | 既存のカードCSV取込と同じプロジェクト内で動くため、同じロック（LockService）で書込を直列化できる。既存の数式・入力規則・CSV照合を同じコードから使える。追加のサーバー・秘密鍵が不要 | Sheets API を画面から直接呼ぶ：Google Cloud の設定が必要、iPhone のホーム画面アプリでは1時間ごとの再認証が不安定、Apps Script の CSV 取込とロックを共有できない。自前サーバー（Cloud Run 等）経由：サーバー・秘密鍵・費用管理が増える。Apps Script の画面だけで作る：指示書で不採用 |

### 費用
GitHub Pages（公開リポジトリ）と Apps Script（個人の Google アカウントの無料枠）を使う。Apps Script には1日あたりの実行時間・URL取得回数などの上限がある。家計簿1人分の利用量では上限に届かない見込みだが、無料を保証するものではない。

## 3. 認証方式（案）

Apps Script のウェブアプリを別ドメイン（github.io）から呼ぶ場合、Googleのログイン情報（Cookie）は送れない。「自分のみ」「Googleアカウントを持つ全員」で公開すると、画面からは通信できない。そのため「全員」で公開し、**アプリ自身の認証を API の中で行う**。

1. 端末の登録はスプレッドシートから行う。スプレッドシートのメニュー「アプリと接続」を押すと、10分間だけ有効な6桁の接続コードが表示される。スプレッドシートを開ける人（Googleアカウントでログイン済みの本人）しかコードを出せない。
2. アプリに接続コードを入力すると、API が端末ごとの鍵（ランダムな長い文字列）を発行する。端末は鍵を IndexedDB に保存する。サーバー側には鍵のハッシュ値だけを保存する。
3. 以後の通信はこの鍵で認証する。鍵のない通信、無効な鍵、取り消された鍵は、データを一切返さない。
4. 端末の紛失時は、スプレッドシートのメニューから端末ごとに取り消せる。接続コードの入力は5回失敗するとロックする。

- 秘密鍵・合言葉をアプリのコードや GitHub に入れない。
- スプレッドシートの共有範囲を広げない（制限付きに戻しても動く）。
- 家族が使う場合も、スプレッドシートを編集できる人が自分で接続コードを出せば、同じ仕組みで追加できる。

## 4. 同期方式（案）

- スプレッドシートを正本とする。端末は「最終取得した内容のコピー」と「未送信の操作キュー」を持つ。
- 新規入力には端末で UUID（取引ID）と操作ID を付ける。操作ID は API 側の処理済み台帳（`_AppSync` を作り替えて利用）に記録する。同じ操作ID の再送には、前回と同じ結果を返す（冪等）。
- 01_Raw_Data には空き列がないため、行の目印は台帳側で持つ。行の内容（B〜I）のハッシュ値と取引IDの対応を台帳に記録し、行の特定に使う。
- 送信済み取引の修正・削除では、取得時の内容ハッシュを一緒に送る。スプレッドシートで直接変更されていれば、上書きせず「競合」として返す。
- 書込は 01_Raw_Data の末尾の空き行への追加だけとし、並べ替えは行わない。追記できる行（数式の範囲）の残りが少なくなったら、エラーとして知らせる。
- 取得は起動時・再表示時・同期後・手動更新で行う。取得した内容で未送信キューを上書きしない。
